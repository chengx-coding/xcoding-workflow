# Goal — a small Minecraft in the browser, offline and 2D

## Requested outcome

Build a playable, offline 2D sandbox game inspired by Minecraft on top of the seed shell in this
repository. It must run by opening `index.html` — no build step, no external libraries, CDNs, fonts,
or network access — must feel like a small Minecraft, must save progress, and must document its
controls.

The deliverable is the product itself: a page a person can open from `file://` and immediately play,
not a scaffold, a demo, or a description of one. The work order runs the full managed lifecycle
(goal, analysis, solution, approval, implementation, verification, result) and records the evidence
that the product is real.

## Requested capability scope (source: user)

| Capability | User wording | Meaning for this product |
| --- | --- | --- |
| Playable 2D sandbox | "playable, offline 2D sandbox game inspired by Minecraft" | Side-view tile world the player can move through, dig, and build in. |

## Quality contract (user-facing)

- **Q1 — Offline integrity.** Opening `index.html` from `file://` loads and plays with zero network
  requests, zero external libraries, fonts, images, or audio files. Every pixel and every sound is
  generated at runtime. No build step exists.
- **Q2 — Minecraft feel.** The first five minutes recognisably feel like Minecraft: punch a tree,
  watch block-break particles and cracks, place blocks, open a hotbar and inventory, craft a
  pickaxe, see a day/night cycle change the sky, light a cave with a torch, and save the world.
  Blocks are chunky, the world is seed-generated and explorable, and the camera follows smoothly.
- **Q3 — Playability.** A person who has never seen the game can move, jump, mine, place, craft,
  save, and find their way back into the world without reading source code. Interaction is
  forgiving: reach limits, placement rules, and mining progress are visible and predictable.
- **Q4 — First-run affordance (applied user requirement).** Every primary system has a visible,
  clickable entry point, tutorial step, or task — not only a keyboard legend or README paragraph.
  A first-run welcome offers a direct way in; a persistent task tracker names the next useful
  action; HUD buttons open inventory, crafting, the guide, the backdrop, saving, and the menu.
- **Q5 — Visual-state backdrop (applied user requirement).** Removed or covered content and every
  mode, theme, time, and viewport change keep a visible before/after context: world-space ghosts
  for recent edits, a HUD before/after indicator that names the changed kind (edit, mode, time,
  view), a minimap viewport trail for zoom and window-size changes, and a sky backdrop that shows
  the day/night transition. Nothing the player changed silently disappears from view.
- **Q6 — Save continuity.** Progress survives reload and re-open: world, player, inventory, time,
  tasks, and settings. Saving is automatic and also explicit; when browser storage is unavailable
  the game says so and offers file export/import instead of losing work silently.
- **Q7 — Documented controls.** An in-product guide lists every control with its effect, and
  `README.md` documents controls, saving, and the offline check commands.
- **Q8 — Experience lens (applied user requirement).** Discoverability, visual review, and
  progression are explicit design lenses used to judge the build, not afterthoughts:
  discoverability through first-run entry points and tasks, visual review through before/after
  state evidence, progression through a task chain that unlocks capability and rewards.

## Reference and signature-experience challenge

The credible domain reference is Minecraft (Java/Bedrock editions) for feel, not for literal
feature parity; the 2D side-view constraint is a deliberate interpretation, not a missing dimension.

Signature experience to reach, from that reference:

1. Breaking and placing blocks is tactile: cracks, particles, sound, tool speed, drops.
2. The world feels alive and cyclic: sky, sun/moon, day/night, ambient detail.
3. Dark places need light: skylight falls off underground and torches push it back.
4. Crafting converts raw gathering into capability: wood → planks → sticks → pickaxe → faster mining.
5. A seed world is worth exploring: varied surface, caves, ore veins, trees.
6. Leaving and returning is safe: the save restores the same world.

The challenge for analysis and solution is to classify each signature capability as must, should,
or deferred with user value and rationale, rather than either omitting the feel or chasing parity.
Deferrals must remain reversible and must not be presented as forbidden.

## Experience lens (proposed)

- **Discoverability.** The first screen always offers a visible way in: a "Play" button, a "Guide"
  button that enumerates controls, and a task list that states the next concrete action. HUD
  buttons mirror the keyboard shortcuts for the six primary systems. Contextual hints appear when
  the situation changes (first block mined, first inventory full, night falling).
- **Visual review.** The game keeps its own change record: recent edits in a before/after strip,
  world-space ghosts in backdrop mode, a minimap with the previous viewport outlined, and a sky
  that shows the passing day. A reviewer can inspect what changed without a debugger.
- **Progression.** A task chain (gather → craft → build → light → survive → explore) gives the
  first session a spine; tool tiers visibly speed mining; the day counter and saved state make
  progress durable.

## Acceptance conditions

- **A1.** `index.html` opens from `file://` in a real browser; the page becomes ready (status ready)
  and renders a non-blank, varied world.
- **A2.** Static scan finds no external reference, network URL, CDN, font, or external asset in any
  page-served file; the app works with no network.
- **A3.** Movement, jumping, gravity, collision, mining (with hardness and tool speed), block
  placement rules, reach, inventory counting, and crafting are implemented and covered by
  executable tests.
- **A4.** Seed-based world generation produces a deterministic world with surface variation,
  caves/ore, and trees; the same seed reproduces the same world; a different seed does not.
- **A5.** A day/night cycle changes the sky and light level; skylight and torch light both affect
  rendering; torches are craftable and placeable.
- **A6.** Saving round-trips world, player, inventory, time, tasks, and settings; a second browser
  load restores a first-load save; storage failure is surfaced with an export/import fallback.
- **A7.** First-run affordance: the initial page shows a welcome with clickable Play/Guide entry
  points and a visible task tracker; every primary system has a visible button or task, verified by
  a browser self-test that clicks DOM controls, not only keyboard events.
- **A8.** Visual-state backdrop: an edit produces a before/after record visible in the HUD and in
  world ghosts; mode, time, and viewport changes each produce a visible before/after indicator;
  verified by browser self-test and by screenshots of the before and after states.
- **A9.** Controls are documented in the product guide and in `README.md`.
- **A10.** Declared checks stay green: `node --test "tests/**/*.test.js"` and
  `python tools/page_check.py`; seed tests are not weakened; no project Git commit is created.

## Scope and constraints

- Product constraints from the user: 2D, offline, `file://`, no build step, no external libraries,
  CDNs, fonts, or network, small Minecraft-like, save progress, document controls.
- Project constraints from `.xcoding/WORKFLOW.md`: English code/comments/README/work-order
  documents, UTF-8/LF, no project Git commit, temporary files under the work order `tmp/`, keep the
  seed checks green, change-report stage waived by the user
  (`work_order.requires_report=false`, `work_order.report_skip_reason=user_waived`).
- Provenance of exclusions: user-sourced constraints are 2D, offline, no build/libraries/CDN/
  network, small scope. Project-sourced constraints are listed above. The goal adds no binding
  exclusion of its own: Minecraft systems that are not requested (mobs, combat, redstone,
  dimensions, multiplayer) are neither required nor forbidden here; analysis classifies them with
  user value and the solution records any deferral with its impact and reversal path.
