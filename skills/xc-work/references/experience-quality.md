# Experience-product quality

**Scope:** task-class. **Promotion status:** `proposed`. **Generality evidence:** the overall experience lens is proposed (one open-sample application);
section 3's visual-state backdrop is owned by the visual output-surface contract and is
validated-in-class only for **interactive visual experience products** where content can be removed/covered or
mode/theme/time/viewport changes. **Applies when** the primary deliverable is a visual/interactive experience
product: a rendered experiential product, or an interactive visual tool whose acceptance is experiential.
**Does not apply** to a pure library, CLI, data pipeline, data dashboard, documentation set, or other
primarily informational deliverable. Record the selection or a not-applicable reason; do not force
this lens on a non-experience product.

This is a review lens, not a feature checklist. It does not add a universal requirement and does not
authorize adding a feature that the request does not support.

## 1. First-run discoverability

For an interactive visual experience product, the first-run affordance is a **must owned by the visual output-surface
contract**; this profile does not restate the rule. Other experience products use the proposed lens.
Verify from a fresh state and link the executed entry-point evidence.
For a rendered product, apply the visual owner's **interaction truth** check when primary controls
exist: a real-pointer test must show the same hit target at pointerdown/up and the advertised effect;
an enabled-looking no-op is a defect. Record the visual review against the task's quality target;
do not prescribe a specific art style or add an unrequested visual feature.

## 2. Visual quality

Visual composition, independent critique and the visual gate are owned by `xc-visual-design`.
Functional-preservation evidence is owned by `xc-verification`. This profile does not restate either
method. Visual quality requires an independent critic; this profile does not authorize a self-review
substitute.

## 3. Visual-state backdrop

For an interactive visual experience product, the state-dependent backdrop is a **must owned by the visual
output-surface contract**; this profile does not restate the rule. Record the linked before/after
evidence; it does not apply to static docs, CLIs or informational dashboards.
## 4. Reference signature and progression

When a credible reference exists, identify a small set of signature capabilities and the genre's
defining loop. Do not silently classify a defining loop as a non-goal. A reference-observed feature
that the request is silent about is a **proposed should**, not an automatic must: record the evidence,
the user value and the experience gap. A user or the request may make it binding; without a user,
record the proposed should and do not add it as a hidden requirement. If a no-user analysis chooses a
smaller scope, record the reason and the lost experience value.

Avoid feature-count thinking. A simple, task-appropriate progression is valid; it must be discoverable
and produce a real state change, not a decorative menu.

## 4b. Reference loop depth and orientation

When the request explicitly names an inspiration/reference and asks the product to feel like it, the
reference's **defining loop is a must at the smallest playable depth**: identify the loop from
evidence and implement it (gather -> process -> build/upgrade is one example, not the rule). Optional
signature features remain proposed shoulds. Do not silently shrink the defining loop; without a user,
a smaller loop requires a recorded exclusion with source, impact and re-entry trigger.

When no explicit reference is named, treat the reference loop as a proposed should: record the
evidence, user value and lost experience; a user may make it binding.

When the product has a navigable world, consider an orientation/map affordance (map, coordinates,
compass, or equivalent). Treat it as a proposed should with the same user/no-user rule; do not force it
on a non-spatial product.

## 5. Verification

When the product is an experience product and the profile is used, record:

- the `xc-visual-design` review record when visual quality is in acceptance;
- a progression/signature journey when one is included;
- the executed evidence and any gap/limit.

A quality gap is recorded; a broken core or unplayable state remains a high-severity finding under
the universal rules. Do not convert an experience gap into a high-severity finding, and do not use
this profile to require a specific feature set.

## 6. Force

Convention-only. No new runtime command, state, node type or configuration surface. The overall experience lens is
proposed; its interactive-visual first-run affordance and visual-state backdrop are validated-in-class; other visual subclasses are not covered. A second
independent experience-product instance is still needed for the overall lens.
