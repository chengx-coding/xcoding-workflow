# 核心设计

本页介绍 XC 的核心设计，并说明它依据什么。

XC 核心设计是 XC 对「XC 的核心是什么」的正式陈述。它给出这份设计所依据的原则、所服务的目的，以及承载规范内容的关注点，连同这些关注点所持有的不变量与判定标准。一次后续改动要对着这份陈述衡量，而不是只对着局部症状衡量。本页以公开解释材料的方式概括这份陈述。

## 一份 workflow，而不是一个 harness

harness 是程序化的运行时。它绑定某一个具体的 Agent 和这个 Agent 手上的工具，负责把事真正跑起来：进程、沙箱、权限、上下文、模型路由与工具调用。

workflow 定义的是事情应该怎么做：先做什么、每一步必须产出什么、什么条件下不许继续、谁来复核结果。它不绑定任何特定工具。只要能正常完成工具调用和 Skill 调用的 Agent，都能照同一套结构执行。

这个区分决定了什么该写进这份设计。把事跑起来归 harness；方法留在这里。两者交接的地方是一个固定的 project bridge，它只提供某个具体项目的事实。

## 这套 workflow 怎么接进一个 Agent 工具

不需要为每个工具写接入插件。接入分四层，每层只管一件事：

- **Skill** 是唯一的接入机制。Agent 工具正是通过它知道 XC 是什么、怎么操作。工具加载的是 Skill 的发现契约，所以这些能力不需要为每个工具单独做适配就能到达所有受支持的宿主。
- **CLI** 装住一切可以做成确定性的东西：调度、状态迁移、完整性校验、标识符生成、schema 校验。同一个输入必然同一个结果的事都属于它，而不是留给模型反复判断。
- **project bridge** 装项目自己那一半——构建与测试命令、语言、边界、约束。它只读一次。通用设计既不猜这些事实，也不替项目填写。
- **workshop** 装持久记录：work order、artifact 与运行时状态。

由此有两类 Skill。**核心 Skill** 说明这个 workflow 是什么、CLI 怎么用、设计里有哪些机制。**专项 Skill** 说明每一个环节怎么做：怎么写 goal、怎么调研、怎么评审。

一条分工决定了一个资产属于哪一类、以及什么该放进 CLI：**确定性的归 CLI，需要判断的归 Skill。**

## 这份设计要解决什么

XC 的存在是为了消除作者在用 Agent 处理复杂任务时反复遇到的四个问题。每一个都能在项目历史里找到依据，不是设想的痛点：

- **有事做不深、做不透。** 调研有方法——已确认的事实、假设与未知项分开，主张要有可引用的证据——而深度由任务的实际情况决定。
- **任务跑着跑着偏离目的。** 结构化的 goal 记录、唯一的进度事实源、以及 solution 与来源绑定，保住了 goal 这份记录。但长过程里是否始终贴着 goal，今天还没有机械保证，设计如实这样写。
- **结果不算错，但不符合项目惯例。** 约定发现有一条强制下限、三级权威（已声明、已配置、未声明的既成做法），以及「违反已声明规则必须记录理由」。
- **过程看不见。** 持久记录保留了进度、artifact 与决定，所以对长期项目的理解不会随着任务数量增加而衰减。

这四条里今天解决了两条，另两条还没有。设计如实标明哪条是哪条，而不是把四条都说成已解决。

## 这份设计怎么组织

从「相信什么」到「要求什么」，共三层：

**四条原则**是判断依据。**谁拥有这份工作**：一份工作的持久状态属于项目，不属于某次对话，也不属于某个厂商的存储；而且一个没有参与这项工作的主体必须能把它重建出来。**接入靠 Skill 与 CLI，不靠插件**：对接一个 Agent 工具不需要单独的接入层。**能检查的才写进去**：一条必须防住「本来就不打算照做的执行」的规则，必须是关于已表示状态的可检查条件；做不到时，设计必须明说。**每件事只有一个出处**。**记录要说得清三种状态**：做完了、根本没查、不适用——没有结论本身也是一种结论。

**三层目的**，每层都带一条失效条款。当目的所依赖的条件不再成立时，它必须被论证地退役，而不是被静默遗忘，这样一条已经被推翻的目的就无法继续以「没人再审视的假设」的形式存活。三层目的是：消除上面那四个问题；对一个没参与这项工作的主体保持可靠；以及能力增长时不增加工作，让增长必须自证价值。

**四个关注点**承载规范内容。每一个都写明自己的主张、具名的不变量、一句用来判断偏离的问题，以及今天的状态：

- **谁拥有工作** —— 每个持久事实只有一个出处，持久内容不得写到这次工作之外，运行时编排树是唯一的进度事实源，没参与的主体要能重建。
- **什么时候管、怎么管** —— 按事实决定投入并在证据不足时从严、声明过的输入要被证明到位才准入、结构由工具拥有并对每个 worker 只投最小必要上下文、推导出来的状态只读不写、终态提交是原子的、没有发生的事也要有一个具名的结果。
- **和外面怎么接** —— bridge 是声明式项目事实的唯一读取点，未声明的约定只走一条有边界、分级的通道，通用资产里不得含环境专属事实，宿主目标由生成而来并检查是否过期，适配器声明的支持程度必须诚实。
- **能力怎么组织** —— 每个能力单元为自己的规则负责，只通过文档里写明的公共参数使用；能力集合可以增加、合并，也可以收缩，而收缩必须先声明触发条件。

## 每条不变量都要声明自己的强制力度

设计要求每一条不变量都说明它今天到底有多硬，词汇表刻意很小而且诚实：

- **机械** —— 有一个能指名的检查、校验器、schema 或运行时状态迁移会拒绝违反。
- **默认** —— 装好就是这个值，偏离是一次显式发布的行为。
- **仅约定** —— 只有契约文字。没有任何东西会拒绝偏离，而文字必须写明这一点。

一条不变量如果没有声明力度，就是没写完。这条要求之所以存在，是因为这份设计自身的执行力就是文档纪律加少量机械检查，读者有权知道哪条是哪条，而不是自己去猜。这三个取值还承担第二件事：当一条义务里确定性的那一半还没有被拆进 CLI 时，诚实的标签就是「仅约定」，而这个标签本身就是一个信号——**有东西本可以做成可检查的，但还没有做。**

## 这份设计不是什么

这份设计对各类任务是通用的。它没有为软件开发单独划出一层：软件开发与软件调研是它的主要应用场景，而不是坐在通用核心之上的一层特化。那个框架里唯一留下来的规则是可以推导出来的，因此保留：**验收标准归领域所有，通过 bridge 提供。**

这份设计也不主张超出实现所提供的东西。运行时记录是「准入与连续性记录」，不是这项工作被正确执行过的证明；完整性校验能发现改动，不认证身份；完成回执是没有签名的自报；查看器是只读的，所以用户是审批而不是就地编辑；已交付的宿主适配器自称「仅验证」。价值主张同样被拆开：成本是可测量的，而收益在存在预先登记的对照之前只能写成「面向……而设计」。

## 怎么对这份设计本身做改动

对整个核心设计的任何调整、改进或变更，都必须在生效前先取得你的确认，而不是由实现者在其他工作中顺手修改。

有三条义务贯穿整个设计，集中写在一处。改动必须按整体架构判断，而不只按局部症状判断——一次让局部症状消失、却让整体变得更纠缠的改动，不应因为局部方便而被并入。改动必须成比例：当更小的正确修复已经足够时，应当复用既有机制，而不是新增命令、状态、配置面或节点类型。规范来源先行：派生物与生成物永不手工编辑，且不得产生需要同步的第二权威。本次修订新增了一条义务：**新得出的结论必须追上还在讲旧结论的文档**——因为这份设计自己的历史里就有一条被后来证据推翻的目的，而文档在那之后仍然在讲它。

本概览概括这份核心设计，使读者能把其余公开文档放在它的框架里理解。它是解释，而不是设计本身，也不声称取代它。
