# 版本维护

**语言：** [English](../../development/versioning.md) | **简体中文**

当前源码版本为 <!-- xc:version -->0.1.0<!-- /xc:version -->。它标识源码候选，不代表公开发行或支持证据已经存在。新快捷入口只存在于包含本次实现的构建；原有安装可继续使用 `xcoding version --json`，重新安装同一历史 wheel 不会获得新能力。受支持的发行边界见[安装契约](../getting-started/installation.md)。

## 单一版本来源

[`pyproject.toml`](../../../pyproject.toml) 的 `project.version` 是唯一可编辑的产品版本来源，使用无前导零的稳定版 `X.Y.Z` 格式。构建元数据、wheel 身份、Bundle manifest 和安装后的版本报告必须一致。协议 schema 版本、宿主 adapter 版本和刻意固定的测试夹具有各自含义，不是产品版本来源。

`xcoding --version` 输出经过校验的已安装包版本 `xcoding <version>`，不接受附加参数。`xcoding version --json` 保留完整机器可读版本及 Bundle 报告，既有裸 `xcoding version` 仍要求 `--json`，缺少时报告 `json-required`。快捷入口使用相同校验，不隐藏安装错误。已安装包与开发检出的版本可以合理地不同，比较时应对应实际产物，而非无关安装。

## 每次迭代都评估，仅经同意才升级

每次 XC 迭代都记录版本评估，包括有理由的 `no-bump`。判断依据是上次已发行版本以来全部尚未发布的变更，而不只是最近一次提交。提交或完成工单不会自动产生新发行版本。承接未决建议时引用其原始决定 artifact 和已发行基线，并将这些引用保留在工单结果中，让下一次评估沿持久证据继续，而非依赖聊天记忆；原决定或发行基线不可用时记录缺口，不得假设没有待发布变更。

| 处置类别 | 何时建议 |
| --- | --- |
| `no-bump` | 暂不需要新的发行身份，例如尚未发布的内部工作，或不改变公开行为的文档与测试维护；记录理由和待处理变更 |
| `patch` | 发行包含向后兼容的缺陷修复或维护，不增加公开能力 |
| `minor` | 发行新增向后兼容的公开能力；在 `1.0.0` 之前，破坏公开契约也使用下一个 minor 版本 |
| `major` | 从 `1.0.0` 起，发行破坏已文档化的公开契约 |

这是本项目的 SemVer 分类，不是消费项目强制使用的编号规则。破坏性的 `0.x` 变更把 `0.N.P` 提升到 `0.(N+1).0`；稳定版 major 提升时清零 minor 和 patch，minor 提升时清零 patch。进入 `1.0.0` 是关于成熟度和兼容性的主动决定，需要明确批准，不会因功能累积而自动发生。公开 CLI 行为、安装或升级契约、包内 Skill 与 agent 契约、兼容性承诺都应纳入评估。即使版本号获批，支持声明的变化仍需独立证据。

在既有 solution、result 或节点 artifact 中保留结构化决定：

```yaml
version_disposition:
  current: <源码版本>
  candidate: <建议版本或null>
  classification: <no-bump|patch|minor|major>
  reason: <该变更集合需要或不需要升级的理由>
  scope: <精确变更范围及累计未发布基线>
  evidence: [<源码及验证证据引用>]
  decision: <not-requested|pending|approved|rejected|deferred>
  actor: <提出建议的Agent或作决定的用户>
  date: <ISO-8601日期>
  consent: <精确用户决定引用或null>
```

修改版本来源前，Agent 必须通过既有主会话 gate 提出候选版本、理由、范围、兼容性影响和同步工作。只有用户对该具体候选及范围的明确同意才授权升级。批准实现功能、自动提交或采用本政策均不足以授权。拒绝或延期时记录决定、保留版本，并把待发布变更带入下一次评估。范围发生实质变化时重新评估并取得对修订建议的同意。批准升级仍不授权发布、创建发行标签或上传产物。

## 同步与验证

具体升级获批后修改 `pyproject.toml`，更新明确标记的当前版本引用，并重新构建派生产物。不要手改生成的 Bundle 或 wheel 元数据。保留历史发行基线、刻意固定的夹具及独立编号的协议版本。

验证和 CI 中运行 `python scripts/check_version.py`。当前引用使用 `xc:version` HTML 注释对标记，形式见本页当前版本声明。检查器依据可信项目元数据检查这些当前引用和适用的 wheel 文件名示例，不把所有历史数字都解释为当前版本。四个当前引用页面为根 README 双语对和本版本政策双语对；其中的 wheel 文件名示例必须使用当前版本，其他位置的历史 wheel 示例不在本检查范围内。缺失或格式错误的必需标记应失败。可选 `--tag vX.Y.Z` 和可重复的 `--release-notes PATH` 输入用于验证所提供标签及发行说明中的精确 `## X.Y.Z` 标题；未提供时，检查器不宣称已验证发行。

候选包装检查必须独立验证预期 distribution 身份、wheel 元数据、Bundle 版本与安装后 CLI 报告。发行准备还应绑定候选 commit、不可变标签、wheel 名称及摘要、Bundle 摘要、完整性与 provenance 产物、支持矩阵证据及双语发行说明。这些输入变化后重新执行检查与评审。版本批准、一致性检查成功和发布批准始终是不同事项。

## 延期决定

此前 agent 定义改名被用户判断为兼容维护，数值升级则在 `0.1.0` 上延期。[安装说明](../getting-started/installation.md)保留这一历史决定；它不是长期例外，也不允许未来变更不经评估。下次累计评估须保留原有理由及尚未解决的公开契约解释问题，后续发行决定可根据证据和明确同意重新审视。
