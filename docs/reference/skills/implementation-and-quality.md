# Implementation and Quality

**Language:** **English** | [简体中文](../../zh-CN/reference/skills/implementation-and-quality.md)

These supporting Skills execute approved changes, explain them to human reviewers, guide technical writing, and assess evidence.

## `xc-change-report`

[Canonical contract](../../../skills/xc-change-report/SKILL.md)

- **Invoke when:** a work order changed analysable code and a human must review that change without opening an IDE: after implementation and verification, and before the result document.
- **Purpose:** turn one work order's change set into a single self-contained offline HTML report plus the coverage manifest that proves every analysable change unit is covered by an analysis, bound to the code it cites, of what changed, why it exists, the design it embodies, and its place in the larger flow. A unit may additionally declare a change class and answer the design dimensions that class requires (motivation, before/after, alternatives, lifecycle, upstream callers and downstream callees, trade-offs, impact), and carry structured depth blocks (a full-width before/after step comparison, a lifecycle table, or a caller/callee table), so the report reads top-down from macro design intent to concrete implementation, with its sections ordered as a funnel (overview, architectural elements, the change-map index, then the per-unit deep dive grouped under the element each unit belongs to and folded as the detail layer) and its wide tables kept overflow-safe; those dimensions are validated for presence and structure, not for correctness. The report's spine is the architectural element: one to seven elements, each with a six-part profile (what it is, how it worked before, how it works now, why it had to change, its promise and boundary, and where to look next), an element map derived from their declared relations when any are declared, rendered as a component diagram of the interfaces each element provides and requires, and a three-answer brief (worst case, rollback, unverified) in the overview; every analysable unit binds to an element or to an explicit `mechanical`/`unassigned` bucket whose counts the report publishes. A standard/full report may add an optional design-topic layer inside the architectural-element section when a decision-level reader question needs an explicit bridge to units, diagrams, or verification. The layer reuses existing anchors, keeps macro diagrams in the report-level diagram region, and leaves minimal reports unchanged. Following a prefer-diagrams default, the caller/callee and before/after depth blocks also derive layered call-graph and before/after flow diagrams automatically; those unit-level diagrams render inline inside the unit they explain, next to their depth block. Sequence interactions may use an optional deterministic SVG carrier, and a change class for which a diagram is the best expression but which carries none earns a non-blocking advisory rather than a failure.
- **Public entry:** required `report_path`, `manifest_path`, `repo_path`, `baseline_commit`, `language`, and `strength`; validation additionally requires `stage`, and `verdicts_path` is required at the final stage; `gate_required` defaults to `false`. The two baseline snapshot directories `baseline_worktree_dir` and `baseline_untracked_dir` stay required in practice, because the validator recomputes the baseline digest from the recorded capture scope together with the baseline commit rather than from the live worktree. The package's own capture command produces them: `python skills/xc-change-report/scripts/capture_baseline.py --repo <repo> --workbench <workbench> --work-order-id <id> [--baseline-worktree-dir <dir>] [--baseline-untracked-dir <dir>] [--format json|keys]`, whose second `--verify-existing` form recomputes the recorded digest from the recorded scope without materialising either directory again, re-verifies the recorded counts against git and the recorded snapshot, and fails closed on any mismatch. Where version control cannot supply the baseline side — the directory is not a worktree, `HEAD` does not resolve, or it resolves to a commit the tools cannot read — the capture fails closed, copies nothing, and reports the named error `baseline_vcs_unavailable` with the underlying reason; the one authorisation for a full tracked-set copy is `--full-tracked-mirror` with a non-empty `--consent-reference` that names the user's explicit decision, and without both nothing is copied. Such a record mirrors content for a tree with no baseline commit: `--verify-existing` reproduces its digest, but no validated change report can be produced from it.
- **Typical usage:** capture the baseline while the worktree is still at its opened state, before implementation touches it: run the capture form once at work order open, which mirrors only the tracked paths that differ from the baseline commit at open into `<workbench>/tmp/baseline-worktree/` and the untracked paths into `<workbench>/tmp/baseline-untracked/`, and records both directories, the dirty-at-open and deleted-at-open path names, and the worktree digest in `<workbench>/tmp/baseline-open-state.json`; every clean tracked path is read back from the baseline commit, so the digest keeps its old value semantics and only its recomputation source is hybrid, and a baseline whose commit can no longer supply a clean path is not a silent gap: the validator's digest recomputation fails with the named error `baseline_worktree_snapshot_commit_unavailable` rather than passing that proof as complete, and a commit that cannot be enumerated at all fails the manifest build closed, so no manifest is written. Then enumerate the change set and publish the manifest, build the skeleton, write the eight required analysis fields for every unit the manifest lists (several units may share one analysis when it declares that it covers all of them), then validate at `stage=coverage` and again at `stage=final` after the accuracy review. Every round regenerates the same single report; a report that went stale after code rework is refreshed instead of failing a node, and the refresh loop is bounded. A work order that resolves to no report captures no baseline at all.
- **Boundaries:** it never edits code and reaches no acceptance decision about the change; the strength tier changes content thickness only, because all three tiers run every mechanical check and the accuracy review; the human gate is optional and closed by default; hash and token checks prove that an analysis is bound to the code it cites, not that it is correct, and the accuracy review that judges meaning can itself be wrong, while the element layer proves that elements exist, carry their six parts and bind every unit, never that the division into elements is the right one.

## `xc-delegation`

[Canonical contract](../../../skills/xc-delegation/SKILL.md)

- **Invoke when:** a Skill delegates one private worker role through the persistent delegated Agent and needs strict profile resolution, capability narrowing, deterministic preparation, or read-only legacy discovery.
- **Purpose:** validate Skill-local worker profiles and compile one node-attempt-bound dispatch envelope without making the private role a persistent Agent.
- **Public entry:** required `skill_root` and `profile_id`; preparation additionally requires exact runtime node/profile packets, project policy, caller constraints, adapter ID, and output path. A dynamic overlay is optional and narrowing-only.
- **Typical usage:** author a profile under the owning Skill's `assets/workers/`, validate it, obtain the exact running-attempt assignment wrapper, call `xcoding delegate prepare`, and dispatch only an authoritative envelope.
- **Boundaries:** v1 never silently falls back to legacy prompts; capability layers only narrow; runtime state and terminal authority remain runtime-owned; current host statements do not claim enforcement without pinned end-to-end evidence.

## `xc-implementation`

[Canonical contract](../../../skills/xc-implementation/SKILL.md)

- **Invoke when:** an approved solution and required gates have established one bounded implementation change.
- **Purpose:** execute exactly one runtime implementation node and record changed paths, validation, baseline impact, and residual risk.
- **Public entry:** required `workbench_path`, `work_scope`, `inputs`, and `artifact_path`.
- **Typical usage:** read the supplied node contract and approved inputs, implement the accepted scope with the minimum sufficient magnitude for the task (`create` maximizes within its quality contract; `change` uses the minimum sufficient change; `repair` keeps the strong minimality presumption), run focused checks, and write the declared artifact. For `create`, the accepted capability matrix is part of the accepted scope: implement every accepted must capability and do not silently drop or weaken a must/should capability. If the accepted scope or a must capability proves insufficient, stop and return to the caller instead of expanding or shrinking it. An adaptive minimal node may combine one coherent implementation with focused verification after its immutable plan receipt is validated.
- **Boundaries:** it does not own decomposition or retries, cannot opportunistically overwrite feature baselines, and reports only through the runtime public command. Scope expansion or shrink is a caller or gate decision, not a worker decision.

## `xc-writing`

[Canonical contract](../../../skills/xc-writing/SKILL.md)

- **Invoke when:** drafting a human-facing technical answer, explanation, document, or report; revising difficult prose; or reviewing clarity while preserving meaning.
- **Purpose:** help readers understand objects, reasoning, and choices while preserving facts, conditions, exceptions, normative strength, and uncertainty. It owns the shared writing method for documents and standalone answers.
- **Public entry:** required `request`; `operation=write|revise|review` defaults to `write`; optional `inputs`, `audience`, and `authoring_requirements`. Each input is an object with `kind=text|path` and a non-empty string `value`; bare strings are not inferred as paths. Revision and review require identifiable target text.
- **Typical usage:** give the current question or writing task and source material, adapt the explanation to the reader, then check the result against its evidence. For example, set `operation=revise` and pass `inputs=[{"kind":"text","value":"The draft is visible only to its author."}]` to revise supplied text without reading a file. Review returns evidence-backed writing findings and local suggestions without editing the source.
- **Boundaries:** it does not replace managed-document structure validation, the document lifecycle, overall quality review, or the caller's authorization. Missing or ambiguous source material is reported rather than invented. User style and language requirements apply; commands, evidence, and material constraints stay exact. It adds no persistent mode, readability score, ISO conformity claim, or guarantee about every future reply or reader.

## `xc-review`

[Canonical contract](../../../skills/xc-review/SKILL.md)

- **Invoke when:** a workflow requires independent assessment of a managed document, solution, code change, diagnosis, or verification evidence.
- **Purpose:** evaluate immutable inputs and produce traceable, severity-ranked findings and a conclusion.
- **Public entry:** required `review_kind`, `inputs`, and `artifact_path`; optional `review_context`.
- **Typical usage:** inspect the requested quality dimensions, ground each required finding in evidence, and write a validated node artifact. For code and solution reviews, also check under-scope (the accepted need or quality bar is not met), over-scope (unnecessary churn or changes beyond the approved scope), and scope drift (the implementation differs from the recorded scope decision). For `create`, check fidelity against the original request plus the accepted capability matrix, not only the approved solution; a material exclusion with no user or project source is an unsourced narrowing. When a reference signature was recorded, a missing or weak signature must capability is under-scope; a signature should capability is under-scope unless the accepted matrix records its deferral with reason and impact; importing unrelated reference features is over-scope.
- **Boundaries:** review is read-only; the caller owns remediation and risk decisions, and raw transcripts are not the default artifact. Scope findings are evidence-backed review judgments, not a mechanical scope checker.

## `xc-verification`

[Canonical contract](../../../skills/xc-verification/SKILL.md)

- **Invoke when:** implementation, diagnosis, adoption, or a feature baseline needs project-defined validation evidence.
- **Purpose:** run the smallest sufficient command set, map evidence to acceptance conditions, and record outcomes and coverage gaps.
- **Public entry:** required `workbench_path`, `verification_scope`, and `artifact_path`; optional `inputs`.
- **Typical usage:** read project verification policy, run focused checks before broader regression checks, and record every command and unexecuted prerequisite. For `create`, map evidence to every must/should capability in the accepted matrix; a passing test suite does not prove an unverified capability. Adaptive regression or multi-environment scopes use separate verification nodes; a fast pace never removes a required scope.
- **Boundaries:** it does not invent commands or pass criteria, silently weaken acceptance conditions, or modify product behavior to force a pass.
